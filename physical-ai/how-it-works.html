Honest one-liner. Today this is a static website. There is no database server. The "database" is a TypeScript file that gets compiled into the JavaScript bundle your browser downloads. Your edits live in your browser's localStorage — they don't reach anyone else's screen until they get committed back into the seed file and the site is redeployed.
Tech stack

The stack in one paragraph

The whole site is a single-page React app written in TypeScript, bundled by Vite, and hosted as static files on Vercel. State management is Zustand (a tiny store library — no Redux). The data is a hand-curated TypeScript seed (~140 companies, ~150 activities). The Excel export uses exceljs; charts use recharts; icons use lucide-react. No backend, no API server, no database, no authentication. Anything "live" that you see in the UI is either (a) in the JS bundle, or (b) in your browser's localStorage.

Frontend

React 19, TypeScript 5.7, Vite 6, Zustand 5, recharts, exceljs.

Build

Vite produces a dist/ folder of static HTML / CSS / JS. Vercel serves it.

Backend

None today. Scripts under scripts/ can run locally; GitHub Actions can run them on a schedule.

Data residency

Where the data actually lives

This is the most important thing to understand. Three places hold data, and only one of them is shared:

The database question

"Do we need actual database engineering?"

Short answer: not for what you're doing today. The "database" here is a glorified spreadsheet that lives inside the website's code. That is fine — and intentional — for an internal single-user tracker where the cost of standing up a real backend (Postgres, auth, hosting, backups) outweighs the benefit. But it has real limits, and you've already hit one of them: edits in your browser don't sync to other devices or other people.

Here are the four options on the spectrum, in increasing order of complexity:

Option A — Stay as-is, but use Export → commit (the recommendation)

You edit in your browser. Click the new "Export my edits" button (coming in the same update as this doc). It downloads a JSON file. You hand it to me / paste it into a PR. We bake it into the seed and redeploy. After the next build, the data is in everyone's bundle.

Build effort: small (export button + import script) Runtime cost: $0 Sharing: via PR / redeploy Latency to live: minutes (after deploy)

Option B — Single JSON file in the repo, edited via a server function

Move the seed out of TypeScript into data.json in the repo. Add a Vercel / Cloudflare serverless function that, when you click "Save", commits the new JSON via the GitHub API. The site re-fetches the JSON on load. Halfway between a static site and a real DB. Adds an auth requirement (so randos can't edit your dataset).

Build effort: medium (auth + 1 function + JSON refactor) Runtime cost: $0–$5/mo Sharing: real-time after Vercel rebuilds (~60s) Latency to live: 1 min after save

Option C — Real database (Supabase / Firebase / Postgres)

Drop the seed entirely. All companies and activities live in Postgres. App fetches from a REST API on load. Add auth so only you (or your team) can write. This is the "proper" answer. Lets multiple analysts edit simultaneously, supports row history, fine-grained permissions, audit logs, full text search, etc.

Build effort: large (schema, RLS, auth, migrations, API layer) Runtime cost: $0–$25/mo (Supabase free tier covers a lot) Sharing: instant, multi-user Latency to live: instant

Option D — Airtable / Notion DB as the backing store

Use a SaaS spreadsheet-database as the canonical data, app reads via their API. Lowest engineering effort; you get a UI to edit data outside the app for free; the app becomes a "view" on top. Downsides: rate limits, API churn, vendor lock-in.

Build effort: medium-small (API client + schema mapping) Runtime cost: $10–$24/mo for the SaaS tier Sharing: instant via Airtable, with API caching Latency to live: seconds

My recommendation for an internal IB tracker: start with Option A (you already have it). If you find yourself wanting your colleague to see your edits live, jump to Option C with Supabase — it's the cheapest "real" DB and only takes a day to wire. Options B and D are middle grounds that you'd outgrow.

Click-by-click trace

What happens when you press "+ Activity" on a company card

End to end, every file touched, in order:

You click the button

JSX in src/components/CompanyProfiles.tsx sets setAddingActivityFor(company). React re-renders and a modal mounts.

The modal opens

src/components/ActivityModal.tsx renders with mode="add" and initial pre-filled with the company's id, subsector, geography. You fill in date, investors, amount, description, source URL.

You click Save

The modal calls useMarketStore().addActivity(payload) from src/lib/store.ts.

Validation

store.ts checks: ISO date format, non-negative deal value, http(s) source URL, company id resolves. If any fail, it returns an error and the modal shows it.

Dedupe

findDuplicateActivity in src/lib/dedupe.ts runs against existing activities. If a fuzzy match is found, the store returns { ok: false, reason: "duplicate" } and the modal asks you to edit the existing row instead.

Create the row

The store builds a new Activity with an id like a-manual-<timestamp>-<random>, plus a synthesized Source row pointing at the URL you provided.

Persist to localStorage

Because the id starts with a-manual-, the store's new override layer (added in this update) routes it through src/lib/overrides.ts → persistNewActivities() → localStorage.setItem("paimt-overrides-new-activities-v1", JSON.stringify([...])).

Update React state

The store sets activities: [newRow, ...state.activities]. Zustand notifies subscribers. Every component that uses useMarketStore re-renders. The new row appears in the Activity Tracker, on the company card, in the charts, in the export.

Next page load

At app startup, store.ts calls loadOverrides() from overrides.ts, reads your localStorage, and merges your manual rows on top of the seed — so your edits persist across refresh.

Click-by-click trace

What happens when you press "Refresh data"

You click the button

src/components/AppShell.tsx calls handleRefresh().

(Optional) POST to a backend endpoint

If a VITE_REFRESH_ENDPOINT environment variable is configured at build time, the page does fetch(endpoint, { method: "POST" }). Today none is configured, so this is a no-op.

Cache-busted reload

The handler appends ?r=<timestamp> to the URL and calls window.location.replace(). The browser fetches index.html from scratch; the new HTML references whatever JS bundle hash was deployed most recently.

Bundle downloads, seed loads, your overrides re-apply

If a newer build is on the server, you get newer seed data. Your localStorage overrides still layer on top because the storage keys don't change between builds.

So today Refresh is really "fetch the latest version of this website." It is not a "go pull fresh data from Gmail / Pitchbook / Crunchbase" button. The Gmail / RSS scripts run as a separate process (locally or in GitHub Actions), produce a PR, and only after that PR is merged + redeployed will Refresh expose the new rows.

Gmail integration design

How the Gmail flow is meant to work

The goal: sweep your inbox for newsletters (The Information, Axios, etc.) and surface every Physical AI funding / M&A / partnership signal it finds — but never write to the public dataset without you approving first.

1. Authenticate Gmail scaffold

OAuth handshake against your Google account, run locally or in a Cloud Function. Tokens never live in the static bundle.

2. Sweep matching newsletters scaffold

A Gmail API query like from:hello@theinformation.com newer_than:7d returns recent threads.

3. Extract company / amount / counterparty scaffold

Regex today (src/lib/gmail.ts: parseGmailCandidate); LLM later. Returns a candidate row.

4. Dedupe against existing rows live

src/lib/dedupe.ts flags fuzzy duplicates so we route them through merge rather than create.

5. Land in the Review Queue live

You see the candidate in the Review Queue tab. Gmail snippets stay private — only sanitized text reaches the published dataset.

6. You approve, merge, or reject manual

Approval logic in src/lib/review.ts strips Gmail IDs, sender, subject, snippets from the publishable Source before it lands in the dataset.

7. Verifier flags stale or unsourced records live

src/lib/verify.ts runs in-app; scripts/verify-data.ts writes a Markdown re-check sheet.

8. Daily cron runs the whole pipeline scaffold

.github/workflows/refresh-data.yml at 14:00 UTC daily. Opens a PR for analyst review — never writes directly.

Build + deploy

How dev becomes prod

From editing a file to it being live in your browser:

# 1. You (or I) edit a file under src/
# 2. Locally:
npm run dev      # Vite dev server, http://localhost:5173
                 # → hot module reload, no rebuild needed

# 3. Before commit, you run:
npm run typecheck  # TypeScript: tsc -b — finds type errors
npm run test       # vitest run — 20 unit tests, must all pass
npm run build      # tsc -b && vite build → dist/ static files

# 4. Push to GitHub. The CI workflow .github/workflows/deploy-pages.yml:
#    - runs typecheck + test + build with VITE_BASE_PATH=/physical-ai-market-tracker/
#    - publishes dist/ to GitHub Pages

# 5. Separately, the deploy used by ai_map_repo uses Vercel:
#    - we copy the contents of dist/ into /Users/.../ai_map_repo/physical-ai/
#    - we commit + push to https://github.com/tishir31/ai_map
#    - Vercel detects the push and redeploys
#    - the /physical-ai/ tab on the AI Map site reflects the change

The point: there is no server-side "save" anywhere. Every "deploy" is "ship a new bundle of static files." If you want the dataset to change, you have to either (a) edit your own browser (localStorage), or (b) cause a new bundle to be deployed.

Get your edits into main

The bridge: localStorage → bundle

Until a real database is added, here is the workflow to move an edit from your browser into the shared bundle so it shows up for everyone after the next deploy:

Edit in the UI

Use the Edit or + Activity buttons on a company card. Your changes are immediately saved to localStorage.

Click "Export my edits" in the sidebar

The Manual Edits panel downloads a JSON file with everything you've added or overridden. (New in this update.)

Send me the JSON (or commit it yourself)

I run npm run import:overrides ~/Downloads/paimt-overrides-<date>.json. The script merges your overrides into the seed files (or a new src/data/seedOverrides.ts).

Commit + redeploy

The change is now in the bundle. Everyone who reloads the site sees it. Your local overrides can be reset (they are now redundant with the seed).

That is the cheapest, most honest version of a "save to main" button without a backend. The day you want this to happen with one click — that is the day to add Supabase.
